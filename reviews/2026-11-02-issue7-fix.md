# Issue #7: transaction ownership

Changed the PID-file protocol to a persistent POSIX `flock` inode. A fully written,
fsynced version marker is published using `link`, which never replaces an existing
pathname. Every runner takes a nonblocking exclusive kernel lock before checking
the marker and pathname identity. Release closes its descriptor and never unlinks.

Upgrade requirements and limitations are in `scripts/README.md`: stop all older
runners before removing a legacy PID file. Mixing protocols is unsafe because old
code deletes unknown markers. Unknown ownership remains a manual recovery case.
macOS/Linux POSIX local filesystems are the supported boundary; network filesystems
and native Windows are not qualified. Noncooperating removal/replacement of the
persistent inode can defeat advisory locking and is prohibited. The lock coordinates
transaction runners, not external editors. Normal process death releases ownership;
a crash before publication can leave an unused temporary file.

## Guard checklist

1. **Unevaluable input:** empty, malformed, legacy, unreadable, nonregular and
   symlink ownership files refuse acquisition. `EPERM` cannot imply a dead owner.
2. **Monotonicity:** no PID probing or stale-age heuristic exists. Empty, arbitrary,
   appended and extreme PID strings all refuse rather than becoming recoverable.
3. **Preconditions:** the production transaction calls acquisition before recovery
   and release in `finally`. Tests exercise actual independent Python processes,
   kernel locking, filesystem publication and forced process death.
4. **Source of truth:** ownership is a held kernel lock, not cached metadata or a
   PID. The version marker distinguishes this protocol; inode identity is checked.
   No derived verification cache is added.
5. **Persistence:** failed acquisition closes its descriptor without deleting or
   replacing the persistent lock. A crashed owner leaves the same inode reusable.
6. **Provenance:** these results exercise local macOS, Python 3.14 and KiCad Python
   3.9.13. They do not establish network-filesystem or Windows support.
7. **Known-bad calibration:** the original review reproduced simultaneous ownership
   during empty PID publication. New subprocess fixtures pause before publication
   and after OS acquisition, proving only one caller obtains ownership. Running
   the replacement-release regression against baseline e1c4793 fails because it
   unlinks the replacement owner's file; it passes with this change.
8. **Fix vs mute:** kernel-held ownership replaces unreliable PID inference; no
   warning is hidden and no missing evidence is promoted to success.

## Validation and cost

`python3 -m unittest discover -s scripts -p 'test_*footprint_swap*.py'`: 20 tests
passed. The identical command with KiCad's Python 3.9.13 also passed all 20.
Seven added tests cover process contention during initial publication and before
acquisition returns, crash recovery, malformed/legacy ownership, read and `EPERM`
failures, replacement-safe release, and symlink/FIFO refusal.

Measured 200 acquire/release cycles per implementation on the same local filesystem,
using `time.perf_counter`, including initialization, fsync and cleanup: baseline
median 0.183 ms / p95 0.233 ms; new median 0.531 ms / p95 0.634 ms. The median added
cost is 0.348 ms per transaction. This is a local sample, not a general latency bound.
